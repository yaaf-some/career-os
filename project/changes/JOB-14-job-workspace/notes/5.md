# Unit 5: triage deck (doc notes)

## For `docs/architecture.md`

- Triage has two modes, a card deck and a list, remembered per browser. Every swipe has a button; keys are S, X, Z, Enter and the arrows.
- A single verdict is held for 3.5 s and flushed on `pagehide`, `visibilitychange` and leaving the screen. Bulk verdicts go at once through `POST /api/triage/batch`.
- Undo history (last 20 verdicts) lives in memory for the browser session. A sent verdict is undone with `restore`.
- `POST /api/triage/batch` now returns `failed: [{job_id, error}]` beside `results`.
- `restore`:
  - sends a never-scored job to `pending_scoring`, not `pending_triage`;
  - removes the pipeline entry only if a Save created it (application id starts `triage-`) and nothing happened since: stage never past `shortlisted`, no dates, follow-ups, notes, links, Gmail threads, calendar events or drafts;
  - returns the kept entry's id in `application_id`, or null.
- Applications saved before this change have plain ids, so `restore` keeps them.
- `restore` still returns a job to the queue when its entry is kept. The web does not send it for a job that has moved further along since the verdict.

## For `docs/trust.md`

- The triage card renders posting text as text only, and links the posting only for `http(s)` addresses.
